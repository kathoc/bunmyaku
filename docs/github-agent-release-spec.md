# GitHubから執筆代理を導入する仕様

2026-09-10。GitHubの導入コマンドで、執筆代理の実行コード、利用中の環境に応じたスキル、共通手順、個人メモリーの入口をまとめて配置する。

## 方針と実装計画

既存のinstall.shとinstall.ps1はGitHubのmain.zipからinstall.pyとsrc/jlangbase全体を取り出す。distribution.pyは同梱リソースを含むパッケージを配布するため、今回追加した執筆代理も既存経路で導入できる。欠けていたのは、ZIPの取得から旧版更新までを通した検証だった。

| 優先 | 案 | 効果 | 難度 | 判断 |
| --- | --- | --- | --- | --- |
| 1 | 既存の導入入口を使う | 一回のコマンドで必要一式が揃う | 低 | 採用。登録処理を重複させない |
| 2 | GitHubと同じ構成のZIPで入口を実行する | 抽出漏れと引数の欠落を検出する | 中 | 採用 |
| 3 | 執筆代理の追加前の公開版から更新する | 個人記録を残して新機能が入るか確かめる | 中 | 採用 |
| 4 | Linux・macOS・WindowsでCIを実行する | OS別の入口を継続的に確認する | 中 | 採用。実行前は未検証と明記する |
| 5 | 再実行で更新を自動判別する | 更新引数を省ける | 低 | 見送り。既存仕様の明示的な更新を維持する |
| 6 | 定期的なバックグラウンド更新 | 導入済み端末を自動追従させる | 高 | 対象外。今回の依頼は導入処理の自動化 |

## 採用する仕様と完了条件

新規導入は既存コマンド、更新は同じ入口に--update（PowerShellは-Update）を付ける。更新では以前登録したツールと個人原稿・訂正・メモリーを保持する。利用者が編集した管理対象ファイルには競合を報告し、上書きしない。

統合テストはGitHubのbunmyaku-main/形式で作ったZIPを、実際のシェルまたはPowerShell入口へ渡す。通信部分だけをローカルZIPのコピーに置き換え、展開と導入は実装をそのまま実行する。旧版は執筆代理追加前の公開コミット227c024を使用する。導入後のコマンドでcontextとwriting-start、writing-taskを実行し、Codex・Claude・Ollamaそれぞれの依頼先を確かめる。

新規導入、旧版更新、個人記録保持、再実行時の明示更新要求をローカルで検証する。公開後はGitHubから実際に取得した配布物を隔離先へ導入し、ローカルZIPの結果と分けて記録する。WindowsとmacOSはCI結果を得るまで成功扱いにしない。

## 実装との照合

既存入口を保持し、新規・旧版更新の統合テストと3OSのCIを追加した。Linuxで配布関連5件が成功し、仕様との差異はない。実GitHub取得と他OSの結果は[検証記録](reviews/github-distribution.md)で管理する。

公開前の全テストは108件成功。変更履歴の2026-09-10節はbunmyakuのwriting-*で執筆・点検・差し戻し・編集・最終受理を経て作成した。点検ではPowerShellの更新オプションを指摘し、修正した。最終稿をwriting-handoffで取得してCHANGELOG.mdへ反映し、9月9日節の全文が変更前と一致することを確認した。変更履歴の日本語lintは指摘なし。途中の原稿とセッションは端末内に保持する。
