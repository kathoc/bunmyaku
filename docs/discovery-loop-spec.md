# 書くことで見方を変える生成ループ

## 目的と原因

従来のcraft-briefは生成前の設計を出力するが、段落を書いた結果を次の生成入力へ返す状態遷移がない。そのため、認識の変化を指示しても、最初から決めた結論を演出するだけになりうる。新機能は段落生成と発見抽出を別の呼び出しにし、その間で実際の本文を渡す。生成APIや個人環境のスキルは前提にしない。

## 採用仕様と計画

1. `WORLD_STATE`は開始時の事実ID・記述・出典の台帳として固定。生成側からの追加・変更は受け付けない。新事実が必要なら外部確認待ちとして停止し、別セッションの開始時に採用する。
2. `NARRATOR_STATE`は暫定見解と対立する見方。段落の引用に基づく発見を理由に更新できる。更新しない段落も許す。
3. 毎回、現在状態と遠い目的地を渡し、本文を1段落生成。その本文を受けて別途発見を抽出する。未執筆の計画だけを交換し、既出本文は保持する。
4. 問いが閉じたかではなく、到達内容と残す対立の説明で終了する。必要な問いが未解決なら完了を拒否。任意の対立は未解決のまま残せる。
5. 言い換えしか出ないときは`stalled`、新事実の確認が必要なら`needs_evidence`。予算停止は`budget_exhausted`とし、完成とは呼ばない。固定段落数・感情曲線・品質点は設けない。
6. CLIは開始・次の要求出力・1段落の受理を扱う。Pythonの`run_loop`はwriterとreflectorを呼び続ける。提供者は利用側が接続する。コールバックを内蔵LLMと呼ばない。
7. 全状態、入力応答、見方の変更理由を一つのJSONへ保持。出力は排他的作成で、既存ファイルを上書きしない。

## 応答契約

`paragraph`、`fact_ids`、`fact_review`、`discoveries`、`narrator`、`open_questions`、`remaining_plan`、`decision`、`reason`、`arrival`を渡す。発見は`id/quote/observation/kind`、kindは`reframe/counterexample/question/deepen/restatement`。認識の変更には`update_reason`と`update_discovery_ids`が必要。事実レビューは`reviewer/status/issues`、statusは`consistent/conflict/uncertain`。consistentはレビュー担当の判断であり、プログラムによる意味的な正しさの認定ではない。

新しい発見、既存の問いの解決、読者に必要な準備のいずれもないcontinueはstalledへ変換する。準備を理由に継続する場合は`preparation`に説明する。説明の真偽や言い換えの意味同一性はコードだけでは保証できない。

完了時は未執筆計画を空にし、到達内容arrivalを記録する。未解決の任意の問いを消す必要はない。予算は呼び出し回数の上限であって、必要な複雑さの規格ではない。
