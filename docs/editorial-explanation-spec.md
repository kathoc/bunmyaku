# 説明を受け取れる順序

## 目的

たとえの設定と抽象語の列挙が、本題より重くなっていました。また、文末の変化を促す指示が複数の入口にあり、自然な敬体より語尾の変化が優先され得る状態でした。これを新規編集v4の判断記録と共通ルールで改めます。

原因の判断は既存コードと指示の読解、および利用者の指摘に基づきます。読者実験による原因の確定ではありません。

## 採用する仕様

調査メモanalogy-research-20260908.mdの20案から、優先6案を採用します。直接説明との比較、説明目的、元の関係の既知性、対応の提示、追加設定と誤解の点検、読者による説明し直しを扱います。既存の意味選択と反復の契約は再利用します。大量候補生成、追加学習、常時の複数モデル審査は費用と実績不足から保留します。

新規editor-requestをv4にします。v1からv3の保存済み要求は従来の契約を維持します。v4はexplanation_reviewとreader_checksを追加します。例の記録は検討した箇所だけに置き、例がなければ空配列と理由を許します。採用した例の本文引用、既知性、対応、本題へ戻る引用を検査します。引用と記録の整合は検査できますが、意味の正しさは保証できません。

reader_checksは本題を説明し直すための質問と、本文に基づく判定基準です。採用例ごとに質問を対応付けます。例がない原稿にも本題の確認を最低一つ用意します。回答は生成時に捏造せず、editor-reader-feedbackで別途記録します。原稿ハッシュと質問IDを照合し、readerとmodelを区別します。記録を作っただけではquality_improvedを更新しません。

説明では、ひとつの意味を理解できるところまで伝えてから次へ進みます。理由は必要な場合に添え、全段落へ同じ型を強制しません。新情報が増えない反復も、理解や印象を深めるなら残します。語尾の比率を下げる目的で常体や呼びかけへ変えません。

## 実装対象

- editorial.pyと新規editorial_explanation.pyでv4の要求と受理を扱います。
- bundle_cli.pyで読者回答のローカル保存を追加します。
- 共通の執筆手順、編集手順、文体、意味、節のルールとスキル入口を更新します。
- Ollamaへ新しい説明・文体ルールを実際のsystem入力として渡します。
- メモリーと索引、および共用referencesへの入口を残します。

## 完了条件

6案の判断が契約に含まれること、不要な例を省けること、未回答を成功扱いしないこと、自然な敬体と有益な反復を許すこと、保存済み要求を維持することが条件です。note改稿、公開、インストール済み環境の更新は今回の対象外です。

今回は実装のみです。テストと動作検証は未実施で、上記条件の実行結果は未確認です。次の確認候補は、v1からv4の互換性、無効な引用と異なる版の回答の拒否、CLIの保存、実際の読者による理解確認です。
