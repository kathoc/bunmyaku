# サブエージェントへ執筆を任せる

## 目的と現状

利用者は「○○について書いて」と依頼し、bunmyakuが執筆指示、点検、差し戻し、次工程への受け渡しを担当する。Claude CodeからはClaudeの、CodexからはCodexのサブエージェントを使う。Ollamaでは既存のローカル接続で役割別に生成する。他ホストへの自動切り替えや生成APIの追加契約を要求しない。

既存のwriting-skill.mdは会話中のAI自身を生成担当とする。Ollama専用の生成ループはあるが、ホストのサブエージェントから返された原稿の受理状態を管理する処理はない。これが今回追加する機能の範囲であり、既存ループの不具合として扱わない。

## 採用する仕様

共通Pythonモジュールagent_writing.pyとbundle_cliのwriting-*コマンドを追加する。CodexとClaude Codeでは生成APIを直接呼ばず、親AIがホストのサブエージェントを呼ぶ。Ollamaでは既存のローカル接続を使う。スキルは共通手順への入口とホスト固有の呼び出し指示を持つ。

工程はdraft → review → edit → review → complete。点検が不合格なら同じ工程の執筆担当へ差し戻す。初稿・編集稿それぞれ既定3回まで修正できる。上限に達した後の不合格はbudget_exhausted、資料不足などの停止はblocked。停止状態を合格に変えるコマンドは設けず、理由を解決した新しい依頼で開始する。中断後は同じセッションから未処理の要求を再取得できる。

briefはrequest、title、audience、purpose、style、sources、constraintsを持つ。sourcesはid、path、quoteを持つ読了資料の配列。空配列も認めるが、資料が要る事実を創作してよい意味にはしない。constraintsは文字列配列。親AIが依頼から整理し、結論に関わる不明点だけ利用者に尋ねる。

必須点検は依頼・題名への応答、事実の裏付け、読者の理解、文体と既存の型、全文の構成と意味の保持。モデルは各項目のpass/revise/blocked、本文引用（欠落の場合は空文字可）、理由、修正条件を返す。passには実在引用が必要で、全項目passのときだけ次へ進む。意味の正しさや実読者の理解は機械の保証範囲外。

要求にrequest_id、工程、役割、brief、点検条件、既存原稿、差し戻し、発見履歴、共通手順の場所を含める。応答のrequest_idを現在状態から再計算して照合する。担当IDは親が実際のツールの戻り値から--agent-idで提出する。点検担当が候補稿の執筆担当と同じIDなら拒否する。これは独立モデルの保証や不正な親への防御ではない。

執筆応答はmanuscriptとdiscoveries（quote/observation/next_actionの配列）を持つ。引用は本文に実在しなければ拒否する。発見を強制せず空配列を認める。親と執筆担当は既存の段落生成・読解・発見更新手順を使い、書く前に結論を固定しない。

セッションのstate.jsonに原稿、点検、担当ID、履歴を保存する。書き込みを排他し、ファイル置換を原子的に行う。完了稿の書き出しは排他取得中に状態を検査し、既存ファイルを上書きしない。任意ファイルの手動改変を防ぐセキュリティ境界ではない。

コマンド:

```text
writing-start brief.json --session DIR --host codex|claude|ollama [--max-revisions 3]
writing-task DIR --out request.json
writing-submit DIR response.json --agent-id HOST_AGENT_ID
writing-handoff DIR --out manuscript.md
writing-run DIR [--model MODEL] [--endpoint http://127.0.0.1:11434] [--timeout 180] [--max-actions 32]
```

writing-runはOllamaセッションだけを実行し、既存Ollamaアダプターで構造化JSONを受け取る。モデルと接続先は最初の実行時に固定し、再開時に変更を拒否する。執筆役・編集役・点検役は別リクエストであり、独立モデルによる評価とは称さない。プロバイダー失敗は状態に理由を保存して処理を中断し、同じ要求から再開可能にする。--max-actionsは一度の実行の呼び出し上限で、原稿の合格条件を緩めない。

文脈容量も`--context-length`で指定する。新規の執筆代理は既定16,384トークンをOllamaへ明示し、セッションに固定する。従来のollama-writeの設定は変えない。応答のprompt_eval_countが容量に達した場合は、入力が切り捨てられた可能性を理由に受理を拒否する。本文を削って点検を通すことや、容量不足のまま合格条件を緩めることはしない。容量を変える場合は新しいセッションを作る。

## 実装と検証の計画

1. 共通の状態遷移とCLIを実装し、正常系、差し戻し、停止、古い応答、自己点検、欠けた点検をテストする。
2. 配布用スキルをホスト別に生成し、共通ルールとメモリー索引へ接続する。
3. 一時ホームへCodex/Claude両方を導入し、実際のランチャーで依頼から最終稿まで通す。既存テストも実行する。
4. 利用可能なホストのサブエージェントで実際の執筆・点検・編集を試す。利用できない環境は未検証と記録する。

完了条件は両ホストへ正しく指示が配布されること、不合格稿と古い判定で次工程へ進めないこと、合格した編集稿だけを書き出せること。自動化は反復する差し戻しと受理の検証に効果があるため、共通Pythonへ実装する。

## 検証結果

Ollama実モデルの初回点検で必須5項目が欠落した。既存アダプターのformat="json"はJSONの形式だけを指定し、応答項目を制約していなかった。公式のStructured Outputs資料の本文を読み、formatにJSON Schemaを渡せることを確認した。執筆代理では役割別のJSON Schemaをformatへ渡し、応答後も共通の受理検査を行う。失敗応答と理由はセッションへ記録する。従来の呼び出しには既存のJSON形式を維持する。[Ollama公式資料](https://docs.ollama.com/capabilities/structured-outputs)

### 自動テストと導入

執筆代理を追加した時点で、`.venv/bin/pytest -q`は106件成功。うち執筆代理と配布の追加テストは32件。状態遷移、各工程の差し戻し上限、古い要求・別セッション・自己点検・不正引用の拒否、停止と再開、Ollamaの応答形式・文脈設定、出力の上書き拒否を検査した。GitHub公開後の追加検証とWindows対応は[配布の検証記録](reviews/github-distribution.md)に記す。

一時ホームの実ランチャーで初稿から編集稿の受理・書き出しまで実行し、Codex/Claude両方の指示と更新時の個人メモリー保持を確認した。この端末にも共通ルール、両スキル、メモリーと索引を更新した。両スキルはquick_validateで有効。compileallとgit diff --checkも成功。この段階の検証はLinuxで実行し、公開後に3OSの配布CIを追加した。

### Codexの実モデル

現在のCodexのサブエージェントへ250字程度の短文を依頼した。別の担当が根拠のない効果の断定を指摘し、初稿を差し戻した。修正稿の点検合格後に全文編集へ進み、さらに別担当の点検を通過してcompleteになった。writing-handoffで完成稿を書き出した。

ローカルの証跡は`output/agent-writing-validation-20260910/codex/`のstate.jsonと、同検証フォルダ内の6組の要求・応答、codex-manuscript.md。生成途中の原稿と実行記録は公開リポジトリに含めない。担当IDは実際のツールから得た`/root/sample_writer`と`/root/sample_reviewer`。これは工程の実動作であり、実読者による品質評価ではない。

### Ollamaと残る検証範囲

ローカルqwen3:4bで実行した。初回の形式不適合を合格扱いせず停止し、JSON Schemaを渡すよう修正した。4,096トークンの実行では本文を扱えない応答が続いた。容量を明示した実行では初稿のprompt_eval_countが16,012、eval_countが137と報告され、題材に沿った本文が返った。最初の実行容量ではこの量の入力を収められない。入力量に合う容量の明示と、API報告値に基づく上限検査を追加した。すべてのモデル側の切り詰めを検知できる保証ではない。

Ollamaの各実行は同検証フォルダのollama、ollama-schema、ollama-contextへ分けて残す。モデルの点検精度は機械検査の保証範囲外。Claude CodeはCLIの存在と配布まで確認したが、Claudeの実サブエージェントによる生成は未実施。

最終のOllama実行は初稿後の点検で、本文に存在しない引用を含むpassを返した。プログラムは受理せず、last_errorへ応答を保存し、status=active、phase=reviewの再開可能な状態で中断した。題材に沿う初稿生成と不正な点検の拒否は確認できたが、このモデルでの完成稿までの完走は未確認。

### 文書の点検

新規手順と仕様、導入案内をlintと通読で点検した。手順と仕様で文長の変動が少ないという警告が各1件あった。条件を明示する技術文書であり、語尾や文長の変化自体を目的とした修正は見送った。導入案内は指摘なし。ルール正本、ホスト別スキル、メモリー索引の三つを導入処理でつないだ。
